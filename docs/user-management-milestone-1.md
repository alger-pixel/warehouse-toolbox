# User Management — Milestone 1

Settings → User Management (`#settings/users`) adds account administration only.
There is no login redirect, user session, filtering of operational cards, or new
authorization requirement on existing warehouse APIs. No deletion is provided.
Nothing automatically creates users or modifies Feishu on page load.

## Configuration

The actual USER CLASS table ID was **not found** in the repository. Set
`FEISHU_USER_TABLE_ID` to the existing table's real ID. Do not create another table.
`FEISHU_TOOL_TABLE_ID` uses the existing TOOL CLASS (`tblNxCev7LS7uETW`).
The existing Feishu config loader also requires `FEISHU_APP_ID`,
`FEISHU_APP_SECRET`, `FEISHU_BASE_APP_TOKEN`, `FEISHU_PACKAGE_TABLE_ID`, and
`FEISHU_CLIENT_TABLE_ID`. The app needs read/write permission for USER CLASS and
read permission for TOOL CLASS. USER CLASS field names are validated before writes;
Timestamps use epoch milliseconds, displayed in America/Toronto.

Before login/authentication exists, **only the new administration endpoints** use
`USER_MANAGEMENT_ADMIN_KEY`: a random secret of at least 32 characters. Missing
configuration fails closed for this feature. Generate a key with
`openssl rand -hex 32` and put it in the ignored `worker/.dev.vars` for local use.
Do not put real secrets in `wrangler.toml`, examples, source, or Git. The UI accepts
the key for the current page only, sends it in Authorization, and forgets it on
locking administration or navigating away. It is not ALGER's account password.
Keep local testing on loopback; hosted use requires HTTPS. For a later approved
deployment, configure this key as a Cloudflare Worker secret, not a plain variable.
No deployment was performed for this milestone.

`USER_MANAGEMENT` is the new Durable Object binding, class
`UserManagementCoordinator`, migration `user-management-v1`. Every request for the
same base and USER CLASS table uses one coordinator. Existing Durable Object
bindings/migrations are retained. A future Worker deployment will need this new
binding/migration as well as the table ID and secret; deploying does not sync users.

## API

All follow the current POST JSON convention and return `{ok, data}` or normalized
`{ok:false,error}`. Send `Authorization: Bearer <administration key>`.

- `/api/users/list`: `{}` → public users, never password hashes.
- `/api/users/get`: `{userId}` → one public user.
- `/api/users/tools`: `{}` → live TOOL CLASS metadata (including non-Active entries
  for identifying old assignments; only Active entries are assignable).
- `/api/users/create`: account, displayName, status (`Active`/`Disabled`), isAdmin
  (boolean), warehouses (array), clients (array), toolIds (array), password, requestId.
  USER ID is server-assigned; omit userId.
- `/api/users/update`: same profile fields plus userId; password omitted or `""`
  preserves the existing hash. A new password resets it without the old password.

`requestId` is a random UUID generated by the editor for each save, reused for
uncertain-response retries. Never include an existing hash. The server whitelist
ignores unrelated fields and never writes CREATED DATE or LAST LOGIN during edits.
No response or diagnostic log contains passwords, hashes, credentials, or raw rows.

## Password storage

Uses the pinned dependency `scrypt-js@3.0.1`, not a bespoke hash or plain SHA-256.
Parameters: **N=32768, r=8, p=3**, 32 MiB working memory, random 16-byte salt from
Web Crypto, 32-byte derived key. This is an [OWASP-recommended scrypt profile](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
Implementation: [scrypt-js](https://github.com/ricmoo/scrypt-js).

Stored format: `scrypt$v=1$N=32768,r=8,p=3$<salt hex>$<derived key hex>`.
A future login service can verify this versioned format. No login verification or
session is introduced now. Passwords are preserved exactly (no trimming or Unicode
normalization), minimum 6 characters with at least one ASCII letter (A–Z, either case) and one
number (0–9), maximum 1024 UTF-8 bytes. No special character or uppercase requirement. Confirmation is
checked in the editor. Blank passwords are allowed only for edits and never erase
U-0001's existing/blank hash. Input byte buffers are cleared after hashing.

The implementation was tested in local workerd (about 0.55 seconds for a hash on
this development machine), and against Node's independent scrypt implementation.
Production latency depends on runtime resources; the hash is executed inside the
serialized administrative Durable Object, not a public unauthenticated hot path.

## Identity, concurrency, and lockout protection

ACCOUNT trims outer whitespace and compares case-insensitively. USER ID never
changes. Creates scan existing `U-<number>` IDs and reserve the next number in
Durable Object storage before a write. The high-water mark survives restart and
prevents reusing a reserved number; gaps after failures are intentional.

Serialized writes re-read USER CLASS and check account/ID conflicts and the current
active-admin count. The resulting state must retain at least one exact
`STATUS=Active` + `IS ADMIN=Admin`. Disabling/demoting the final admin is rejected
by both UI and API. U-0001's blank initial hash does not block its password setup.
Active admins conceptually override warehouse/client/tool restrictions, including
future Tool IDs (`hasToolAccess` helper); no global enforcement calls it yet.

Writes persist a pending intent containing only the intended Feishu fields
(password already hashed), never the plaintext password. The request fingerprint
is HMAC-SHA256 keyed by the administration secret, not an unkeyed password digest.
Successful request receipts contain only public user data. A lost response is
reconciled against the original desired fields before another write; successful
retry neither creates another user nor rehashes the password.

If a write is unconfirmed and the original fields are not visible in Feishu,
**further writes fail closed** with WRITE_UNCONFIRMED. Read/list still works. Retry
Same Save rechecks the record. If it persists, an administrator must inspect the
USER CLASS record and the coordinator's pending operation; there is deliberately
no automatic second create or browser-side override. Do not clear a pending intent
without confirming whether the external write happened. This is a conservative
boundary because Feishu does not provide atomic conditional writes/unique indexes.
Out-of-band edits or another writer that bypasses this coordinator are not serialized.
Request receipts are retained in the coordinator for this small administrative v1;
no password/plaintext session is stored in localStorage, sessionStorage, or receipts.

## Access assignment

TOOLS come from live TOOL CLASS, not the frontend registry and not a hardcoded list.
Each list row shows name, warehouse, client, and immutable Tool ID. Multiple checkbox
selections can be assigned right-to-left or removed left-to-right. Normal users only
see Active available tools in the selected warehouse **and** client scope. Admins
see all Active tools. Scope choices derive from TOOL CLASS plus existing user scope
values. Unknown/retired assignments remain visible for removal; incompatible tools
are never silently dropped. The server independently validates IDs and relationships.
Values trim, deduplicate, and serialize to pipe-delimited text. Tool IDs retain case
and stable identity. Warehouse/client choices with no current tool can be retained
from existing records; arbitrary new scope entities are not created in this editor.

## Local testing

From `/Users/algerou/warehouse-toolbox`:

```sh
npm --prefix worker ci --ignore-scripts
node --test worker/test/*.test.js tests/*.test.cjs
```

These suites use fixtures only. They do not read or write live Feishu.

For interactive testing with the **local Worker**:

1. Set the required bindings and real USER CLASS ID in ignored `worker/.dev.vars`.
   Do not overwrite existing configuration with the example. Add a locally generated
   `USER_MANAGEMENT_ADMIN_KEY`. The real Feishu credentials still address a real
   table: pressing Save in this setup writes USER CLASS, even though the Worker is local.
2. Start the Worker in a terminal:

   ```sh
   cd /Users/algerou/warehouse-toolbox/worker
   npx wrangler dev --local --port 8787
   ```

3. Start the static frontend in another terminal:

   ```sh
   cd /Users/algerou/warehouse-toolbox
   python3 -m http.server 5501 --bind 127.0.0.1
   ```

4. Open `http://127.0.0.1:5501/#settings/users` or
   `http://localhost:5501/#settings/users` and reload the page after updating files.
   User Management automatically uses `http://localhost:8787` on these two exact
   origins; no console override is required. Production and all existing operational
   API calls retain the deployed Worker URL. There is no fallback to production if
   the local Worker is unavailable. In Network, verify `/api/users/list` and
   `/api/users/tools` target `http://localhost:8787`.
5. Enter the local administration key in the form. Confirm ALGER loads, edit it,
   and verify final-admin status controls are disabled while password reset remains
   available. Add a normal user, select scope, assign tools, and save. Reopen with
   blank password inputs, change only the display name, and verify dates/hash
   preservation via tests or the administrative Feishu table. Test light/dark mode
   and narrow screens. Lock Administration clears the key and any pending edit.

If the table ID or key is missing, only User Management shows a configuration error;
Dashboard, Settings appearance, B044, TINECO, and existing operational APIs stay open.
No public login, deletion, TOOL CLASS mutation, or access enforcement was added.

## VS Code Live Server reload loop

If users/tools both return 200 but the screen resets to “Administration access
required”, check for an automatic document reload. Live Server on port 5501 was
observed sending `reload` about 300 ms after Wrangler created SQLite `-wal`/`-shm`
files in `worker/.wrangler/state/v3/do`. Reloading correctly clears the in-memory
administration key and restores the initial screen; this is not a response-envelope
or Feishu single-option parsing mismatch.

The shared `.vscode/settings.json` excludes `worker/**` and Wrangler-generated
folders from Live Server's watcher, retaining its existing default exclusions.
**Stop and restart VS Code Live Server** after pulling/changing this setting; a
browser refresh alone does not rebuild its watcher. Keep the local Worker running,
open `http://127.0.0.1:5501/#settings/users`, enter the administration key, and verify
ALGER remains visible after both requests complete. Frontend HTML/JS/CSS changes
still reload normally. Alternatively use the documented Python static server,
which has no automatic reload watcher.

Read-only diagnosis confirmed the real local responses were `{ok:true,data:[...]}`:
one user (U-0001 / ALGER, Active, isAdmin=true) and three tools. The shared API client
returns the same array under `data`; User Management expects exactly that array.

Available Tools has independent Warehouse and Client filters, populated dynamically
from TOOL CLASS, with All Warehouses / All Clients defaults. They combine with AND
and only narrow the available list; assigned tools and stored access scopes do not
change when filtering. Scope validation and Active Admin semantics are unchanged.
